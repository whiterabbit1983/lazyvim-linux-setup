# Результат проверки

## Текущая версия: Git и плагины Neovim

В отдельном контейнере **Ubuntu 24.04 x86_64** проверены:

- Реальный блок установки Git из `install.sh`: изначально команды `git` не было, APT установил Git. При втором запуске блок использовал существующий `/usr/bin/git` без повторной установки пакета.
- `bash -n` и ShellCheck для `install.sh`, `tests/smoke.sh`, `tests/git-smoke.sh`.
- `python3 tests/upstream_versions.py`: **9 тестов**. В том числе ветки существующего/отсутствующего Git для APT/DNF/Pacman и совпадение отдельного `config/git.lua` со встроенной в установщик конфигурацией.
- Настоящий LazyVim starter с текущими плагинами и точной конфигурацией Git из установщика. Для целевого теста отключена автоматическая загрузка не относящихся к Git языковых инструментов и парсеров.
- `tests/git-smoke.sh`: код завершения `0`. Проверены обнаружение изменённого фрагмента Gitsigns, параметры отображения, включение/выключение blame строки и наличие всех 6 горячих клавиш.
- Через Fugitive проверены status, добавление файла в индекс, создание локального коммита, blame, вертикальный diff и история.

Тестовые коммиты создаются только во временном репозитории; автор задан локально, push не выполняется. Этот тест не проверяет интерактивное написание сообщения коммита или отправку изменений на сервер.

Полный установщик языковых окружений и оба Python-режима после этой Git-правки заново не запускались. Для Fedora/Arch команды установки Git проверены с подменой пакетного менеджера в unit-тестах, не реальной установкой. Предыдущие полные проверки приведены ниже.

## Версия `dde9c8f`: upstream-релизы, Linux Mint и опциональный Python

Установка проверена от непривилегированного пользователя с `sudo` в контейнере `linuxmintd/mint22-amd64:latest`, x86_64. Digest образа: `sha256:34ff53d1dca48a73486c3051425306421278225ae02b6d5066a3c940183cae1f`.

Это **образ для сборки пакетов Mint 22**, с репозиторием `packages.linuxmint.com wilma` и Ubuntu Noble. Его `/etc/os-release` сообщает Ubuntu 24.04.5 LTS: это не полноценная настольная установка Mint. Определение `ID=linuxmint` и вариантов `ID_LIKE` отдельно проверяется unit-тестом реального кода установщика.

Успешно выполнены:

- `bash -n install.sh`, `bash -n tests/smoke.sh`, ShellCheck.
- `python3 tests/upstream_versions.py`: 6 тестов. Проверены числовое сравнение версий, исключение RC/nightly, выбор Current вместо принудительного LTS, отсутствие Python по умолчанию, порядок флагов, ошибка при изменившихся upstream-данных и определение Mint/LMDE.
- Полная установка `bash install.sh --yes`: код `0`. Новый Python в mise **не установлен**; проверено отсутствие каталога `mise/installs/python`. Используется системный Python 3.12.3.
- Полный `tests/smoke.sh` после установки по умолчанию: код `0`.
- Повторная полная установка `bash install.sh --yes --with-python`: код `0`.
- Python 3.15.2 действительно собран из `https://www.python.org/ftp/python/3.15.2/Python-3.15.2.tar.xz`. Он установлен в пользовательский каталог mise; проверены SSL, SQLite, bz2/lzma/zlib/zstd, ctypes, readline, tkinter, pip и venv.
- Полный `tests/smoke.sh --with-python`: код `0`.
- В обоих режимах работают сборка/проверки тестовых проектов и подключение LSP: `rust-analyzer`, `gopls`, `basedpyright`, `ruff`, `vtsls`.
- После сборки нового Python `/usr/bin/python3` по-прежнему сообщает 3.12.3; вывод версии до и после сравнен через `cmp`.

На рабочей macOS-машине установщик не запускался. Версии выше — результат конкретной проверки, а не зафиксированные версии установщика.

## Предыдущая версия: дополнительные проверки

Первоначальная версия также проверена в отдельном контейнере **Ubuntu 24.04, x86_64**. В частности, были проверены резервные копии и повторный запуск:

- `bash -n install.sh` и `bash -n tests/smoke.sh`.
- `shellcheck install.sh tests/smoke.sh`.
- `--help`, отказ при запуске от root, отказ при неизвестном параметре.
- Первичная установка всего набора.
- Повторная установка финальной версии скрипта: код завершения `0`.
- Резервное копирование всех 4 каталогов Neovim: контрольные файлы сохранились.
- Повторный запуск не дублирует строки загрузки PATH в `.bashrc` и `.zshrc`.
- Установка всех 14 явно перечисленных Mason-пакетов.
- Rust: `cargo check`, `cargo fmt --check`, `cargo clippy`.
- Go: `go build ./...`.
- Python: создание `.venv`, `py_compile`, `ruff check`.
- TypeScript: компиляция через локальный `npx tsc`, выполнение результата через Node.js.
- C и C++: компиляция и выполнение минимальных программ.
- Инициализация и подключение LSP-клиентов к буферам Neovim: `rust-analyzer`, `gopls`, `basedpyright`, `ruff`, `vtsls`.
- Весь `tests/smoke.sh`: код завершения `0`.

## Не проверено

- Полноценная настольная установка Linux Mint, Mint 21, LMDE, Fedora, Arch, отдельная установка Debian и aarch64. Для Mint/LMDE дополнительно проверен только выбор APT-ветки; для Mint 22 — установка с его пакетными репозиториями в указанном контейнере.
- Интерактивный интерфейс, шрифты, X11/Wayland clipboard, Zsh-сессия.
- Работа отладчика, все операции LSP и все форматтеры.
- Интеграция ESLint с реальным проектом и полное завершение загрузки каждого Tree-sitter-парсера. Парсеры могут доустанавливаться при первом открытии редактора.
- Полный аудит безопасности всех upstream-пакетов.

## Предупреждение npm audit

Во время проверки `npm audit --omit=dev` для Mason-пакета `eslint-lsp` сообщил **3 high-уведомления в одной цепочке зависимостей**:

`vscode-langservers-extracted` → `vscode-markdown-languageservice` → `picomatch`.

Основной advisory: [GHSA-fc5q-39xc-vjpf](https://github.com/advisories/GHSA-fc5q-39xc-vjpf), ReDoS в `picomatch`. Это сообщение об upstream-зависимости, а не доказательство эксплуатации через данную конфигурацию. Достижимость уязвимости из ESLint LSP не проверялась. Другие инструменты на базе того же пакета, включая JSON LSP, также требуют внимания.

Автоматический `npm audit fix --force` **не запускался**: npm предлагает несовместимую замену версии пакета. Скрипт не скрывает вывод npm и не изменяет вручную зависимости, которыми управляет Mason. Следите за upstream-обновлениями; не считайте успешный smoke-тест аудитом безопасности.

Для `vtsls` и `prettier` тот же npm-аудит не сообщил известных уязвимостей на момент проверки.
